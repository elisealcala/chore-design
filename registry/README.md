# Component registry (unreleased)

The catalog builds local shadcn item JSON; it is not a published release. Run `pnpm install --frozen-lockfile`, `pnpm build`, and `pnpm registry:build` from the repository with Node 22.22.0 and pnpm 10.9.0. Built artifacts are in `registry/dist/<item>.json`. In a configured React/TypeScript shadcn project, run its compatible shadcn CLI with `add /absolute/path/to/registry/dist/<item>.json`. The project must already have React and matching React DOM, the shared tokens and the appropriate Tailwind 3 preset or Tailwind 4 adapter, and a valid `components.json` alias for its UI directory. The CLI resolves aliases to either root or `src` layouts; it may access shadcn's color metadata and package registry during installation. Add all wanted item paths in the same command. Review changes before accepting them.

The catalog provides Button (primary/secondary), Input, Textarea, Label, Card, Badge, Table, Select, Checkbox, Dialog, Tabs, Separator, Container, PageIntro, Section, and EmptyState. Checkbox, Dialog, Tabs, and Separator declare `radix-ui` 1.6.7; Select uses the native HTML select and its platform popup; use their accessible labels and dialog titles/descriptions, and maintain visible focus. Set `aria-invalid` and associate error text with `aria-describedby` on form fields. Apply the profile and theme attributes on an ancestor and explicitly style the application surface with `bg-background text-foreground`. Variants and styling may be adapted in the installed source. The source belongs to the consumer; changing or rebuilding this registry does not change installed projects. Do not overwrite local edits without review.

`pnpm registry:fixtures` builds the catalog and creates four disposable clean React installations in `test-results/installed`, covering Tailwind 3.4.17/4.3.3 and root/`src` layouts. It installs dependencies from npm, invokes the pinned shadcn CLI, captures and validates draft baselines from installed source, then typechecks and builds each example. The fixtures use checked-in npm lockfiles. Run `pnpm test:registry` after fixture creation to exercise the installed examples. Fixture results are not evidence that an existing application was onboarded. React 19 is the fixture target; other React versions, primitive families, and production frameworks require their own verification.

## Baselines for later upgrades

For every installed item, capture the exact UTF-8 content and SHA-256 digest of each installed file after CLI transformations, together with its consumer-relative POSIX path, item version, and release identifier, in a record conforming to the `baseline` contract in `docs/stage-1/DATA-CONTRACTS.md`. Validate with `@chore-design/contracts`; reject duplicate paths and overlapping item ownership before recording. Preserve the original baseline when customizing local source. Compare original, local and incoming source during a future upgrade and advance the baseline only after a successful validated update. Fixture baselines use a draft identifier solely for validation; the current draft has no stable release identifier and does not automatically write consumer adoption records or apply upgrades; that orchestration is Stage 4 work.
